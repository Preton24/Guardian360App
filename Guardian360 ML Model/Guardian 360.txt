The overall goal is:

Build a reliable fall-detection system using an ESP32 + MPU6050, eventually combining rule-based detection and ML, with the final model capable of running on/alongside the ESP32.

We are currently in the dataset + ML preparation stage. We have not trained the ML model yet.

2. 🧠 First We Built a Rule-Based Fall Detector

Before ML, we created a conventional fall detector using thresholds.

The idea was that a fall usually has a sequence somewhat like:

Normal movement
      ↓
Free fall / reduced acceleration
      ↓
Impact
      ↓
Body orientation changes
      ↓
Person becomes relatively still

Initially, our firmware used a state machine:

NORMAL
   ↓
IMPACT
   ↓
SETTLING
   ↓
ANALYZING
   ↓
FALL_CONFIRMED
      or
NOT_A_FALL

4. 📊 Features Used in the Rule-Based System

Instead of looking at only one axis, we calculate the magnitude.

Total acceleration
accMag = √(ax² + ay² + az²)

When the device is stationary, acceleration magnitude should be approximately:

1g

because gravity is being measured.

Total gyroscope magnitude
gyroMag = √(gx² + gy² + gz²)

This tells us how much rotational movement is happening.

5. 🚨 Initial Fall Rules

We used thresholds such as:

Impact
acceleration >= 2.0g

This detects a strong sudden acceleration.

Stationary condition
0.75g <= acceleration <= 1.25g

This indicates the sensor is experiencing approximately normal gravity without large movement.

Stillness
gyro <= 30 °/s

This helps determine whether the person has stopped moving after the potential impact.

Timing

We used:

Settle period = 700 ms
Analysis period = 2300 ms

So the system doesn't immediately declare a fall after one large acceleration spike.

6. 🖥️ Serial Output Was Also Improved

7. ⚠️ We Then Identified the Limitations of Threshold Detection

A simple:

if acceleration > 2g → FALL

isn't reliable enough.

For example:

Normal activity can cause high acceleration

Someone could:

jump
run
sit down quickly
drop the device
hit something
swing their arm

and generate a high acceleration spike.

So:

High acceleration alone does NOT mean a fall.

8. 🧩 We Improved the Concept to a Multi-Stage Fall Event

We discussed using evidence from several stages:

FREE FALL
   ↓
HIGH IMPACT
   ↓
ORIENTATION CHANGE
   ↓
POST-IMPACT STILLNESS

Instead of:

HIGH IMPACT → FALL

we want:

multiple pieces of evidence → FALL

This is much more robust.

9. 🕳️ Free-Fall Detection

A potential fall may involve a period of reduced acceleration.

For example:

accMag < ~0.5–0.7g

This can be used as supporting evidence.

So a sequence like:

0.4g
0.5g
0.6g
     ↓
2.8g
3.1g
     ↓
1.0g
1.0g
1.0g

is much more suspicious than:

2.8g
     ↓
1.0g
10. 🔄 Orientation Change

Another useful feature is how much the person's body orientation changes.

For example:

Standing
   ↓
Fall
   ↓
Lying down

The accelerometer can help estimate the gravity direction and therefore orientation.

We discussed using something around:

>45° orientation change

as supporting evidence, rather than requiring it.

Why?

Because not every real fall produces exactly the same orientation change.

11. 🧍 Post-Fall Stillness

This is particularly useful.

Suppose:

High impact
     ↓
Person continues moving normally

That's probably not a fall.

But:

High impact
     ↓
Person remains almost motionless

is much more suspicious.

So we proposed measuring:

acceleration stability
gyro stability
percentage of samples satisfying stillness
12. 🧮 We Also Discussed a Fall Score

Rather than a single hard condition, we can assign points.

For example:

Event	Score
Free fall	+2
High impact	+2
High rotational movement	+1
Orientation change	+2
Post-impact stillness	+3

Then:

score >= threshold
        ↓
     FALL

For example:

threshold = 6

This is more flexible than requiring every condition.

31. 📉 We Need a Common Sampling Rate

There are several possibilities.

Option A — Keep SisFall at 200 Hz

2 seconds:

200 × 2 = 400 samples

That's a lot of input data.

Option B — Use 50 Hz

2 seconds:

50 × 2 = 100 samples

This is much easier for an ESP32.

Option C — Use 100 Hz

2 seconds:

100 × 2 = 200 samples

This is a good compromise.

For Guardian 360, 100 Hz is currently a strong candidate, but we'll decide this explicitly before implementing the windowing stage.

33. 📐 ADXL345 Conversion

The SisFall documentation gives the conversion formula:

Acceleration [g]
=
[(2 × Range) / 2^Resolution] × raw_value

For ADXL345:

Range = ±16g
Resolution = 13-bit

Therefore:

scale = (2 × 16) / 2^13
      = 32 / 8192
      = 0.00390625 g/bit

So:

ax_g = ax × 0.00390625
ay_g = ay × 0.00390625
az_g = az × 0.00390625
34. 🔄 ITG3200 Conversion

For the gyroscope:

Range = ±2000 °/s
Resolution = 16-bit

Therefore:

scale = (2 × 2000) / 2^16
      = 4000 / 65536
      = 0.06103515625 °/s per bit

So:

gx_dps = gx × 0.06103515625
gy_dps = gy × 0.06103515625
gz_dps = gz × 0.06103515625
35. ➕ We Also Calculate Magnitudes

The normalized dataset will contain:

Acceleration magnitude
acc_mag_g =
√(ax_g² + ay_g² + az_g²)
Gyroscope magnitude
gyro_mag_dps =
√(gx_dps² + gy_dps² + gz_dps²)

These are useful because they provide orientation-independent overall movement measures.

38. 🚨 One VERY Important ML Decision We Haven't Forgotten

We must not randomly split individual rows/windows into train and test.

Why?

Suppose:

Subject SA01
    ↓
Trial D01
    ↓
100 windows

If we put:

70 windows → training
30 windows → testing

the model has effectively seen almost the exact same person's movement in training.

That can give us a falsely impressive accuracy.

Instead:

SUBJECTS
   │
   ├── TRAIN subjects
   │
   ├── VALIDATION subjects
   │
   └── TEST subjects

This is called a subject-independent split.

That is much more meaningful for Guardian 360.

41. 🎯 Why False Positives Matter

Imagine Guardian 360 says:

FALL DETECTED!

every time the person sits down quickly.

That's bad.

Likewise, if someone actually falls and the system says:

NORMAL

that's potentially much worse.

So we especially care about:

Fall recall

How many actual falls did we detect?

and:

False-positive rate

How often did we incorrectly call normal activity a fall?
